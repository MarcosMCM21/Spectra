# Registro de Decisões Técnicas e de Produto (`DECISIONS.md`)

> **Instrução para o Agente:** Este arquivo separa estritamente **Decisões Confirmadas** de **Suposições/Pontos Condicionais**. Nunca viole uma Decisão Confirmada.

## 1. Decisões Confirmadas pelo Usuário (Imutáveis sem ordem explícita)

| ID | Decisão | Detalhamento e Justificativa |
| :--- | :--- | :--- |
| **DEC-01** | **Exclusão Total de Voz/Microfone** | A aplicação é estritamente para compartilhamento de tela e mídia. Toda comunicação por voz fica no Discord. Não existem botões de microfone nem permissões `microphone` no LiveKit. |
| **DEC-02** | **Salas Fixas (Persistentes)** | As salas não expiram. Recebem um código permanente único gerado pelo Hub, aparecem em "Acesso Rápido" e podem ser acessadas por código/link. O servidor LiveKit aloca recursos apenas quando há pessoas conectadas (com *grace period* de 5 min ao esvaziar). |
| **DEC-03** | **Conta persistente por apelido e senha** | Cadastro e login usam apelido exclusivo e senha, sem e-mail/confirmação por e-mail; o cadastro confirma a senha. Web e Desktop podem usar contas diferentes; cada conta lista suas salas próprias e as salas em que entrou. O Hub mantém um token interno para autorizar ações nas rotas existentes; ele não substitui a senha nem é exibido como fluxo de recuperação. |
| **DEC-04** | **Bot de Música Server-Side (Alta Fidelidade)** | O addon de Spotify / YouTube Music funciona como um **Bot-Participante** em container que publica áudio estéreo (`256–320 kbps`) direto no LiveKit, controlado pela gaveta lateral (`sidebar`) e Mini-Player no Header, sem exigir login ou conta Premium dos ouvintes. |
| **DEC-05** | **YouTube Integrado ao Grid do Showroom** | O addon de vídeo do YouTube opera como mais um card no Grid de transmissões, podendo ser expandido no Modo Foco como qualquer compartilhamento de tela. |
| **DEC-06** | **Moderação pelo Perfil do Participante** | Clicar no avatar de um membro no Dock inferior abre o menu de contexto. Para o `admin`, exibe ações para encerrar transmissão ativa, bloquear compartilhamento de tela, expulsar (`kick`), banir ou transferir host. |
| **DEC-07** | **Pacote de UX/QoL Avançado** | Incluídos no escopo: **Smart Zoom** para telas Ultrawide (`21:9`/`32:9`), **PiP Transparente Click-Through** no Electron, **Gamepad UI** (navegação por controle), **Toggle Expresso AV1**, **Replay Buffer** (`Alt+F10`), **Modo Teatro/RPG** e **Telemetria de Simuladores**. |
| **DEC-08** | **Stack Monorepo e Desacoplamento** | `pnpm` + `Turborepo`, Fastify + SQLite + Zod no Hub, React + Vite + Tailwind + Zustand no Frontend, Electron no Desktop. `shared-ui` nunca importa `electron` ou `livekit-client`. |
| **DEC-09** | **Grafo de Dependências Topológico Fixo** | Ordem única permitida via Turborepo `^build`: `@spectra/contracts` (base, sem deps internos) → `media-client` / `shared-ui` / `addon-sdk` → `hub` → `web` / `desktop`. Todos os pacotes são ESM (`"type": "module"`) e herdam de `tsconfig.base.json` com `strict: true`. |
| **DEC-10** | **Scripts de Validação em Wrapper Fino** | A lógica real permanece em `.cline/scripts/`; `scripts/validate-architecture.mjs` e `scripts/sync-cline-workspace.mjs` apenas delegam a execução via `spawnSync`, preservando a interface pública `node scripts/<script>.mjs` usada por `AGENTS.md` e `/verify-and-test`. |
| **DEC-11** | **Permitir Builds Pós-Instalação (pnpm 12)** | pnpm 12.15 bloqueia scripts de build por padrão (`ERR_PNPM_IGNORED_BUILDS`). A allowlist fica em `pnpm-workspace.yaml` → `allowBuilds: { better-sqlite3, electron, esbuild, @rolldown/binding-win32-x64-msvc }`, pois são exigidos pelo projeto (addon nativo SQLite, binário Electron, esbuild do tsx e binding nativo do rolldown usado pelo Vite 8). |
| **DEC-12** | **Baseline de Dependências Atualizadas** | Todas as dependências fixadas na última versão estável do registry: `turbo 2.11.10`, `zod 4.6.7`, `livekit-client 2.23.0`, `react`/`react-dom 19.3.1`, `@types/react(-dom) 19.3.0`, `@vitejs/plugin-react 6.1.2`, `vite 8.3.5`, `zustand 5.0.16`, `better-sqlite3 13.0.3`, `fastify 5.12.7`, `livekit-server-sdk 2.19.2`, `@types/better-sqlite3 9.6.0`, `@types/node 26.6.6`, `tsx 4.23.15`, `electron 45.1.0`. |
| **DEC-13** | **TypeScript Adiado em 5.x (Major 7 Pendente)** | O monorepo permanece em `typescript ^5.9.3` embora a `7.0.2` já seja a tag `latest`. A migração para TS 7 (port nativo *tsgo*) é major e exige validação separada de `isolatedModules`, `declaration emit` e plugins do Vite/Electron antes de ser aceita. |
| **DEC-14** | **Engine Mínima Node `>=22.12.0`** | Elevada de `>=20` para casar com o requisito declarado pelo Electron 45 (`engines.node >= 22.12.0`). Runtime local validado em Node 26.12.1. |
| **DEC-15** | **Identidade do Projeto: `Spectra` / Escopo `@spectra`** | O nome oficial do produto é **Spectra**. O escopo npm é `@spectra/*` (e o pacote raiz chama-se `spectra`), alinhado ao nome do diretório e evitando ambiguidade com o componente arquitetural "Hub". O tipo base de pacotes do workspace em `packages/contracts` passa a chamar-se `SpectraPackage`. |
| **DEC-16** | **Entry Point Único: `src/index.ts` → `dist/index.js`** | Todo pacote do workspace (`hub`, `desktop`, `contracts`, `media-client`, `shared-ui`, `addon-sdk`) mantém a fonte em `src/index.ts` e declara `"main": "./dist/index.js"`. O Desktop não usa `src/main.ts` nem `"main": "./dist/main.js"` — manter essa convenção evita o colapso de `electron .` (`MODULE_NOT_FOUND`) que derrubava todo o grafo do Turbo em `pnpm dev` (exit 1, `0 successful / 7 total`). Se a Fase 3 optar por renomear para `src/main.ts`, a alteração deve ser sincronizada no `main` e validada com `pnpm dev`. |

| **DEC-17** | **Validação Zod via `validatorCompiler` próprio no Fastify 5** | O Hub declara schemas de rota como Zod puro (`ZodRouteSchema`) e resolve a parte validada pelo campo `httpPart` da definição recebida. Os tipos `FastifyRouteSchemaDef` / `FastifyValidationResult` devem ser importados de `fastify/types/schema.js` (a raiz do `fastify` 5 não os expõe). Falhas retornam o payload padrão `{ error, code: "validation_failed", issues }` (`validationFailure` de `@spectra/contracts`). |
| **DEC-18** | **Hash único para Chaves e Códigos de Acesso** | `secret_token_hash` (`users`) e `rooms.access_code_hash` usam HMAC-SHA-256 determinístico derivado de `HUB_SECRET` (`AccessCodeHasher`), permitindo comparação em O(1) sobre o hash armazenado. Senhas continuam com `scrypt` autocontido (algoritmo + parâmetros + salt embutidos na string). |
| **DEC-19** | **Rota de moderação exige a chave do ator no corpo** | `POST /api/rooms/:slug/moderation` recebe `actor_secret_token` (`SecretTokenSchema`) além de `action` e `target_identity`; o Hub deriva a identidade do admin resolvendo o hash contra `users.secret_token_hash` e valida papel `admin` em `room_permissions` antes de qualquer ação no LiveKit. |
| **DEC-20** | **Palco automático, foco por seleção e tela cheia independente** | O palco abre em grade apenas com transmissões ativas. Clicar em uma transmissão a fixa no painel principal e envia as demais para uma coluna lateral rolável. Tela cheia é uma ação visual independente e nunca muda a seleção em foco. |
| **DEC-21** | **Áudio da janela sem fallback para loopback global** | A Web solicita áudio da janela/aba e descarta qualquer faixa de monitor ou origem não identificada. O Desktop não publica áudio enquanto não houver captura isolada por aplicativo; loopback global não deve ser apresentado como áudio da janela selecionada. |
| **DEC-22** | **Código de recuperação de senha** | Cadastro e redefinição emitem código aleatório de 256 bits, armazenado no Hub somente como HMAC. O usuário deve copiar ou baixar o código e confirmar que o guardou antes de seguir; enquanto não confirmar, o login ou a retomada de sessão emite um código novo para evitar perda se a página for fechada. A redefinição exige apelido + código + nova senha confirmada e gera um código substituto. |
| **DEC-23** | **Código permanente compartilhável da sala** | O Hub gera para cada sala um código permanente único de 10 caracteres, sem símbolos ambíguos; o usuário não precisa definir slug. O código é independente dos códigos de acesso temporários. Salas privadas continuam exigindo sua senha mesmo quando encontradas pelo código. Slugs internos existentes são preservados para compatibilidade com rotas e sessões LiveKit. |
| **DEC-24** | **Identidade LiveKit exclusiva por conexão** | Cada entrada autenticada recebe um sufixo aleatório na identidade LiveKit; a identidade estável da conta continua sendo usada pelo Hub para permissões. Assim Web e Desktop podem entrar na mesma sala simultaneamente. A moderação consulta participantes ativos para aplicar bloqueios, banimentos e remoções a todas as conexões da conta. |
- **COND-01 — Sidecar Nativo de Captura (Fase 5):** A implementação do Sidecar nativo em C#/.NET ou Rust (via *Windows Graphics Capture API*) é **condicional** e só deve ser iniciada caso os testes reais da Fase 3 no Electron apresentem gargalo de CPU ou limitação de bitrate em `4K60`.
- **COND-02 — Topologia de Hospedagem:** A aplicação suporta tanto *Self-Hosted Local* (fibra com 200+ Mbps de upload e IP público sem CGNAT) quanto *VPS em São Paulo* (ex: Oracle Cloud ARM), configurável apenas trocando variáveis de ambiente no `deploy/.env`.
